4. State Management Strategy & Form Validations

Strict separation of concerns to avoid performance bottlenecks across the four applications.

🌐 Server State (React Query)

Manages asynchronous data from backend controllers (Products, Orders, Deliveries).

  • Automatic caching, background refetching & deduplication.
  • Optimistic updates on instant actions (e.g. liking item, driver online switch).
  • Calls invalidateQueries instead of manual state array mutation.
📦 Global Client State (Zustand)

Manages synchronous, app-wide client UI state across disparate components.

  • Stores theme preference, active user session tokens, and sidebar toggles.
  • Multi-step form wizard buffers (e.g. multi-step address checkout).
  • Zero boilerplate, small bundle size, and fast selectors.
📝 Form Handling & Zod Schema

React Hook Form combined with Zod for non-rendering high-speed inputs.

  • Uncontrolled form inputs to eliminate lag during rapid typing.
  • Strict Zod schemas enforce Indian phone format, pincodes, & geo-points.
  • Direct mapping of validation errors to inline red helper text on blur.

5. Critical Unhandled Edge Cases (Not Implemented in Application)

Real-world production failure scenarios that are currently missing or unhandled in the codebase, with architectural solutions and code recipes.

CRITICAL 1. The "Elevator / Basement" Offline Handover Loss
Delivery Partner App
Failure Scenario: A delivery partner enters an underground basement parking or apartment elevator to hand over clothes to the buyer. When the driver taps "Verify OTP" or "Complete Delivery", cellular connectivity drops to zero. The standard Axios call fails with ERR_INTERNET_DISCONNECTED. The driver gives the customer the package, but the app never syncs the delivery. The order remains "Out For Delivery", the driver is never credited earnings, and customer sees an open order.
Recommended Solution: Implement an IndexedDB-backed offline mutation queue using @tanstack/react-query-persist-client with localForage or a Workbox Background Sync Service Worker. Save failed mutations with idempotent idempotency keys; automatically replay when the online window event fires.
Solution Recipe: Offline Mutation PersistenceReact Query Persister
// partnerFrontend/src/services/offlineQueue.js
import { persistQueryClient } from '@tanstack/react-query-persist-client';
import { createAsyncStoragePersister } from '@tanstack/query-async-storage-persister';
import localForage from 'localforage';

const asyncStoragePersister = createAsyncStoragePersister({
  storage: localForage,
  throttleTime: 1000,
});

export const enableOfflineQueue = (queryClient) => {
  persistQueryClient({
    queryClient,
    persister: asyncStoragePersister,
    maxAge: 1000 * 60 * 60 * 24, // 24 hours offline survival
  });

  window.addEventListener('online', () => {
    queryClient.resumePausedMutations();
    toast.success('Network restored: offline deliveries synced successfully!');
  });
};
CRITICAL 2. Flash-Sale Stale Price Desync During Checkout
Customer App
Failure Scenario: A customer adds a jacket to their cart during a midnight flash deal at ₹999 (discounted from ₹1,899). The customer keeps the tab open and falls asleep. The flash sale expires at 6:00 AM, and the seller price reverts to ₹1,899. At 8:00 AM, the customer clicks "Place Order" without refreshing. Currently, if the backend uses the cart's cached price without revalidating against live product stock, the company loses ₹900 per transaction!
Recommended Solution: Implement a Pre-Flight Price Verification step in the checkout flow. Before initiating payment, call POST /api/cart/verify-pricing. If price discrepancies exist, return 409 Price Changed, highlight the changed items in an alert modal with a diff, and ask the user to confirm the new total before proceeding.
Solution Recipe: Pre-Flight Price Check InterceptorCheckoutWizard.jsx
// frontend/src/features/checkout/hooks/useCheckout.js
const handleCheckout = async (payload) => {
  const priceCheck = await api.post('/api/cart/verify-pricing');
  if (priceCheck.data.hasDiscrepancy) {
    // Stop order submission and alert user
    openModal({
      title: 'Price Updated in Cart',
      message: `Items in your cart changed price while you were away:`,
      items: priceCheck.data.discrepancies, // e.g. [ { name: "Silk Shirt", old: 999, new: 1899 } ]
      onConfirm: () => submitOrderWithNewPrice(priceCheck.data.newTotal)
    });
    return;
  }
  return placeOrderMutation.mutate(payload);
};
HIGH 3. Multi-Tab Split-Brain Cart Race Condition
Customer App
Failure Scenario: A customer has RapidCloth open in two browser tabs. In Tab 1, they add an item with a 15% bundle discount. In Tab 2, they remove a companion item. If Tab 1 proceeds to checkout, the client store still believes the bundle discount is active, but the backend rejects the calculation, leading to an unexplained checkout error and abandoned purchase.
Recommended Solution: Use the native browser BroadcastChannel API to synchronize cart mutations across all open tabs in real-time. When any tab modifies the cart, broadcast a message so all other tabs immediately invalidate their cart query.
Solution Recipe: Cross-Tab Broadcast ChannelcartSync.js
// frontend/src/utils/cartBroadcast.js
const cartChannel = new BroadcastChannel('rapidcloth_cart_channel');

export const notifyCartUpdated = (updatedCart) => {
  cartChannel.postMessage({ type: 'CART_UPDATED', cart: updatedCart });
};

export const listenToCartChannel = (queryClient) => {
  cartChannel.onmessage = (event) => {
    if (event.data.type === 'CART_UPDATED') {
      queryClient.invalidateQueries(['cart']);
      toast.info('Cart updated from another tab');
    }
  };
};
HIGH 4. WebSocket Reconnection Thunder Herd & Missed Dispatches
Delivery Partner & Customer Apps
Failure Scenario: When the backend server restarts during deployment, hundreds of driver sockets disconnect simultaneously. When the server comes back up, all sockets reconnect at the exact same millisecond, overwhelming the Node.js event loop. Furthermore, orders dispatched during the 10-second downtime are lost forever because the driver was disconnected and no catch-up mechanism exists.
Recommended Solution: Configure randomized jittered exponential backoff in Socket.io client options, and bind a reconnect event listener that immediately pulls fresh state from GET /api/delivery/orders/current.
Solution Recipe: Socket Jitter & Catch-Up Syncsocket.js
// partnerFrontend/src/services/socket.js
import { io } from 'socket.io-client';

export const socket = io(import.meta.env.VITE_BACKEND_URL, {
  reconnection: true,
  reconnectionAttempts: Infinity,
  reconnectionDelay: 1000,
  reconnectionDelayMax: 10000,
  randomizationFactor: 0.5, // Adds jitter to eliminate thunder herd!
});

socket.on('reconnect', () => {
  console.log('🔄 Reconnected to dispatch gateway — pulling missed orders...');
  // Force catchup of missed dispatches
  queryClient.invalidateQueries(['currentOrders']);
});
HIGH 5. GPS Drift & False Delivery Verification
Delivery Partner App
Failure Scenario: Urban high-rises cause GPS signal reflection (multipath drift) of up to 400 meters. A driver 3 blocks away might experience a GPS glitch placing them at the customer's doorstep, allowing them to tap "Reached" prematurely. Even worse, rogue drivers using mock location apps can simulate being at the address while in another zone.
Recommended Solution: In the partner app, check the browser's coords.accuracy before permitting the "Reached" button. If accuracy is > 50 meters, warn the driver. On the backend, enforce a strict Haversine distance check between driver coordinates and order delivery coordinates (must be ≤ 100 meters).
Solution Recipe: GPS Accuracy & Distance GuarddeliveryValidation.js
// partnerFrontend/src/utils/geoGuard.js
export const verifyArrivalProximity = (currentPos, destination) => {
  if (currentPos.accuracy > 50) {
    throw new Error('GPS accuracy is too low (' + Math.round(currentPos.accuracy) + 'm). Please wait for a clear satellite lock.');
  }
  const distance = calculateHaversine(currentPos.latitude, currentPos.longitude, destination.lat, destination.lng);
  if (distance > 0.1) { // 100 meters
    throw new Error('You are ' + Math.round(distance * 1000) + 'm away from the customer delivery address.');
  }
  return true;
};
MEDIUM 6. Mobile Browser Out-Of-Memory Crash on 48MP Photos
Seller Frontend
Failure Scenario: A seller using a mid-range Android phone takes four 48MP raw photos (15MB each) of clothing items and uploads them via the seller dashboard. When the browser attempts to draw 4 uncompressed images to an HTML canvas or read them into base64, mobile Chrome exceeds its 300MB tab memory limit and immediately crashes to a white screen.
Recommended Solution: Use an off-main-thread Web Worker compression pipeline (like browser-image-compression) to resize photos down to 1200px max width and convert them to progressive WebP at 80% quality *before* assembling the FormData.
Solution Recipe: Off-Thread Image CompressionimageCompressor.js
// adminfrontend/src/utils/imageCompressor.js
import imageCompression from 'browser-image-compression';

export const compressProductImage = async (file) => {
  const options = {
    maxSizeMB: 0.8, // Max 800KB
    maxWidthOrHeight: 1400,
    useWebWorker: true,
    fileType: 'image/webp'
  };
  try {
    return await imageCompression(file, options);
  } catch (error) {
    console.error('Compression error:', error);
    return file; // Fallback
  }
};
HIGH 7. JWT Expiration Mid-Checkout Wizard (Cart Loss)
Customer App
Failure Scenario: A user spends 15 minutes reviewing clothing specifications, picking matching socks, entering a delivery address, and selecting payment method. By the time they click "Submit Order", the short-lived access token (15 mins) has expired. The naive Axios interceptor intercepts the 401 Unauthorized and forcefully redirects the user to /login, losing their entered address and cart state!
Recommended Solution: Implement a transparent Axios refresh token interceptor with request queuing. When a 401 is encountered, pause outgoing requests, silently request a new access token from /api/auth/refresh-token, update headers in memory, and retry the original checkout request seamlessly.
Solution Recipe: Silent Token Refresh InterceptoraxiosClient.js
// frontend/src/services/apiClient.js
let isRefreshing = false;
let failedQueue = [];

apiClient.interceptors.response.use(
  (res) => res,
  async (error) => {
    const originalRequest = error.config;
    if (error.response?.status === 401 && !originalRequest._retry) {
      if (isRefreshing) {
        return new Promise((resolve, reject) => failedQueue.push({ resolve, reject }))
          .then(token => { originalRequest.headers['Authorization'] = 'Bearer ' + token; return apiClient(originalRequest); });
      }
      originalRequest._retry = true;
      isRefreshing = true;
      try {
        const { data } = await axios.post('/api/auth/refresh-token', {}, { withCredentials: true });
        store.dispatch(setToken(data.token));
        failedQueue.forEach(prom => prom.resolve(data.token));
        failedQueue = [];
        return apiClient(originalRequest);
      } catch (err) {
        failedQueue.forEach(prom => prom.reject(err));
        window.location.href = '/login?redirect=' + encodeURIComponent(window.location.pathname);
      } finally {
        isRefreshing = false;
      }
    }
    return Promise.reject(error);
  }
);
MEDIUM 8. Concurrent SuperAdmin FastZone Split-Brain Overwrite
SuperAdmin Portal
Failure Scenario: SuperAdmin A opens Zone 104 to add 3 new pincodes (560045, 560046). SuperAdmin B simultaneously opens Zone 104 to change the assigned local hub admin. SuperAdmin B saves at 12:00:01 PM; SuperAdmin A saves at 12:00:03 PM. SuperAdmin A's save completely overwrites SuperAdmin B's admin assignment because neither the UI nor the backend uses optimistic concurrency locking (`__v`).
Recommended Solution: Pass the document's Mongoose __v version key in the update payload. If the version in the database has incremented since the form was opened, reject with 409 Concurrency Conflict and display a visual side-by-side diff merge dialog.
Solution Recipe: Version Lock & Conflict ResolverZoneEditor.jsx
// superadmin/src/pages/ZoneEditor.jsx
const updateZone = async (zoneData) => {
  try {
    await api.put(`/api/superadmin/zones/${zoneId}`, {
      ...zoneData,
      version: currentZone.__v // Send current version
    });
    toast.success('Zone updated successfully');
  } catch (error) {
    if (error.response?.status === 409) {
      openConflictModal({
        currentServerData: error.response.data.serverZone,
        yourChanges: zoneData,
        onResolve: (mergedData) => updateZone(mergedData)
      });
    }
  }
};
